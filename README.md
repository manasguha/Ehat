# Energy Consumption Forecast

**Assignment 12 — Energy Consumption Forecast**

> Objective: predict future energy use.
> Inputs: **Time, Speed, Load**. Output: **Energy consumption**.
> Steps: create sequential data, train a regression model. Outcome: **trend graph**.

This repository implements exactly that brief, end to end: a sequential hourly
simulation of one electric delivery van, a road-load model that makes the target
physical instead of random, three regression models compared on held-out hours, a
24-hour ahead forecast, a Streamlit dashboard, and the figures/deck for the
presentation.

---

## How the assignment maps onto the code

| Brief item | Where it lives | What it does |
|---|---|---|
| **Sequential data** | `src/data_generator.py` | 120 days × 24 h = 2,880 hourly rows in time order, with an AR(1) driving-conditions term so consecutive hours are genuinely dependent |
| **Input: Time** | `src/preprocessing.py` | `hour_sin`, `hour_cos`, `dow_sin`, `dow_cos` — cyclic encoding, because 23:00 is one hour away from 00:00, not 23 |
| **Input: Speed** | `src/data_generator.py`, `src/preprocessing.py` | average speed of the hour (km/h), from a congestion profile plus telemetry noise |
| **Input: Load** | `src/data_generator.py`, `src/preprocessing.py` | payload on board (kg); the depot loads a different amount each day, so Load is not a restatement of the clock |
| **Output: Energy consumption** | `src/data_generator.py` | kWh consumed in the hour, from the road-load equation below |
| **Train regression model** | `src/models.py` | Linear Regression, Polynomial Regression (degree 2), Random Forest |
| **Trend graph** | `figures/11_forecast_vs_actual.png`, dashboard → *Forecast* | observed hours followed by the next 24 hours |

### The physics behind the simulated target

```
P_wheel = Crr · m · g · v  +  0.5 · ρ · CdA · v³          (W)
energy  = (P_wheel / 1000) / η_drivetrain / cycle_penalty  (kWh per hour)
        + auxiliary_load(hour)
```
with `m = 2200 kg kerb + payload`, `Crr = 0.014`, `CdA = 2.24 m²`,
`η = 0.88`, and a 20% penalty below 30 km/h for stop-and-go losses.

Consequences that the report relies on:

* the target is **cubic** in speed (aerodynamic drag), so a straight line cannot
  fit it — which is exactly what the model comparison shows;
* **Load** enters through rolling resistance, so it only matters while the van
  moves (a Speed × Load interaction);
* the van is parked 05:00–22:59 outside its service window, so overnight hours
  carry only the auxiliary load (~0.55 kWh/h) and the target is skewed.

## Results

Chronological split: the last 20% of hours (576) are held out; the models train
only on the earlier 2,304 hours. A random split would have trained on hours that
come *after* the test hours, which is the classic way to make a forecasting
result look better than it is.

| Model | MAE (kWh) | RMSE (kWh) | MAPE (%) | R² |
|---|---|---|---|---|
| Linear Regression | 3.10 | 4.26 | 74.1 | 0.8645 |
| Polynomial Regression (deg 2) | 2.21 | 3.40 | 23.3 | 0.9139 |
| **Random Forest (deployed)** | **2.20** | 3.42 | **13.5** | 0.9127 |

24-hour ahead forecast backtest (planned duty cycle only, no peeking):
**MAE 1.73 kWh**, RMSE 2.85 kWh, MAPE 11.4%.

Reading the table honestly:

* **Linear regression loses badly** (MAE 3.10 kWh, MAPE 74%) — the target is
  cubic in speed, so a single slope cannot work. That is the evidence for
  non-linearity, not a formality.
* **Polynomial and forest are close, and the metrics disagree.** Degree 2 has the
  best R² and RMSE; the forest has the lowest MAE and by far the lowest MAPE
  (13.5% vs 23.3%). The deployed model is chosen on **MAE**, because MAE is in
  kWh — the same unit as the answer, and the number an operator can act on.
* **MAPE flatters the forest** because it is sensitive to the near-zero parked
  hours; the report says so rather than quoting it alone.
* **Degree 4 overfits** — R² falls back to 0.88 (`models/degree_sweep.csv`).
* **Autoregressive lags help but are not deployed.** Adding the previous hours'
  consumption improves MAE by 0.24 kWh (`models/sequential_feature_experiment.csv`),
  but at forecast time those values do not exist. The deployed model is not
  autoregressive on purpose.

## Dashboard

Seven pages, all reading the same saved artifacts, so nothing on screen can drift
from the pipeline output: **Overview, Energy Predictor, Forecast, Model
Comparison, Trend & Seasonality, Sensitivity Analysis, What-If Scenarios**.

The app does not retrain on startup: it loads `models/*.pkl`, then re-evaluates
the loaded models on the same seeded chronological split to build the comparison
table. If an artifact is missing or incompatible the app warns and trains
in-process instead of crashing.

## Deployment (Streamlit Community Cloud)

1. Main file path: `dashboard/app.py` (this repository/branch).
2. Streamlit installs dependencies from `dashboard/requirements.txt` — the file
   next to the entrypoint, as Community Cloud expects for an app in a
   subdirectory.
3. Pick a subdomain, e.g. `energy-consumption-forecast`.
4. Point the QR code on the final slide at the resulting URL.

Two caveats worth knowing before the demo: the free tier **sleeps when idle**, so
the first request after a pause can take 20–30 s; and the app must be set to
public in **Settings → Sharing**, otherwise visitors hit a sign-in wall instead of
the dashboard.

## Limitations and future work

* The data is **simulated**, not measured: the model inherits the road-load
  assumptions above, and 8% multiplicative noise plus the hidden driving-condition
  state cap how accurate any model can be.
* Residuals remain autocorrelated (`figures/13_residual_autocorrelation.png`),
  because driving conditions are genuinely unobserved. A sequence model (LSTM,
  gradient boosting on residuals) is the natural next step — but it needs the
  previous hours' consumption, which is why the deployed model does not use it.
* One vehicle, one duty cycle, no weather, no road gradient, no traffic-signal
  data, and no battery state of charge.
* The forest cannot extrapolate: speeds above ~90 km/h, or payloads above 1,200 kg,
  are outside its training range.
* At exactly 0 km/h in the middle of the day the forest is outside its training
  region (the van is only ever parked overnight); the dashboard detects this case
  and reports the observed auxiliary baseline instead of a fabricated number.
